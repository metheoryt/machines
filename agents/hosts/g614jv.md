## Native Windows

### Claude config bootstrap — run via Git Bash, NOT PowerShell
- Claude Code runs on win32 and reads `C:\Users\methe\.claude`. To (re)link the
  tracked config there, run the bootstrap through **Git Bash** (`HOME=C:\Users\methe`):
  `& "C:\Program Files\Git\bin\bash.exe" agents/bootstrap.sh`.
- Do NOT run `bash agents/bootstrap.sh` from PowerShell — that `bash` resolves to
  **WSL's**, whose `HOME=/home/me`, so it links the repo into the WSL home instead
  of the Windows `.claude` that Claude Code actually uses. Symptom: a newly-added
  hooks/skills/agents entry shows up missing on Windows (e.g. the SessionStart
  `gortex-onboard-check.sh` "No such file or directory" error) even though a WSL
  bootstrap reported success.

### Port 22 is answered by Windows sshd, not WSL
On this box, port 22 may be answered entirely by Windows' own OpenSSH server
(banner `OpenSSH_for_Windows_9.5`), not the WSL distro's sshd — a key in the
WSL distro's `~/.ssh/authorized_keys` has zero effect if only Windows sshd
listens. For the admin Windows account the trusted-keys file is
`C:\ProgramData\ssh\administrators_authorized_keys` (ACL: SYSTEM +
Administrators), not per-user `~/.ssh/authorized_keys`.

### GitHub SSH identities (two accounts)
- Windows `~/.ssh/id_rsa` = **metheoryt** (default `git@github.com`); `~/.ssh/id_ed25519` = **cyphy671**, used via the `githubcyphy` host alias in `~/.ssh/config`. Verify with `ssh -T git@github.com` / `ssh -T git@githubcyphy`.
- **The Windows-side alias is hand-maintained, NOT repo-managed.** `tier_ssh_accounts` only runs on POSIX boxes, and `windows.ps1` never writes account aliases — so this box's `~/.ssh/config` keeps whatever was typed into it. That is why the name here (`githubcyphy`, no hyphen) drifted from the POSIX side, and why the 2026-07-28 rename to `<user>.github.com` did **not** reach it. Renaming it here is a manual edit plus a remote rewrite on every affected clone.
- `metheoryt` owns machines, airdrome, vasya, etc. **`qaz-code` is moving cyphy671 → metheoryt** (transfer requested 2026-07-28), after which `cyphy671` keeps only the `laws` repo, which is deliberately never cloned locally. Local clones of qaz-code (`GitHub\qaz-law` here, `~/gh/qaz-code` in Ubuntu-26.04) still point at `git@githubcyphy:` / `git@github-cyphy:` and need their remotes repointed to `git@github.com:metheoryt/qaz-code.git`. GitHub redirects the *path* after a transfer, but a retired **host alias** does not resolve — so leaving the old alias in a remote fails at DNS, not at GitHub.

### Apps & tooling quirks
- **Google Drive's streaming mount letter is auto-assigned, not pinned** — unplugging
  another removable drive (USB / backup SSD) can shift it to a different letter on the
  next boot and break any app config that hardcodes the old letter (e.g. an Obsidian
  vault registered at `I:\Мой диск\…`). Pin it under Google Drive settings.
- **AyuGram** (the Telegram fork installed here) is a *portable* winget package whose
  `tdata` session folder lives next to the `.exe` in the winget package dir, NOT under
  `%APPDATA%` — a winget update can wipe it, and two `tdata` folders can't be merged
  (replace wholesale). Back it up before updating.

### Tooling gotcha — PowerShell tool + `wsl … bash -c`
- Invoking `wsl -d <distro> -u me -- bash -c '…$var…'` **through the PowerShell tool loses shell variables** (they expand empty) and cwd falls back to the `/mnt/c` Windows dir. Fix: write the script to a file with LF endings (use the Bash/Git-Bash tool) and run it via `wsl -d <distro> -u me -- bash /mnt/c/…/script.sh`.

### Split toolset between Git Bash and WSL
- Windows Git Bash has `just` + `pwsh` but **no `jq`**; the default WSL distro
  (Ubuntu-26.04) has `jq` but **no `just`** — so verifying a `just`+`jq` pipeline
  (e.g. `just provision`) means running the recipe's shell body inside WSL, and the
  literal `just provision` invocation is deferred to a real nixos/`jq`+`just` box.
- **The WSL distro that hosts the Orca worktrees has no ffmpeg, no Docker daemon
  and no reachable Redis.** So ffmpeg merge/split postprocessors and any
  Redis-backed path cannot be exercised there — only extraction/metadata work is
  verifiable locally; the rest must be reasoned about or run from the Windows
  checkout.
  - **`command -v docker` is a false positive there.** Docker Desktop mounts its
    CLI at `/Docker/host/bin` and that dir is on `PATH` in every distro regardless
    of the WSL-integration toggle, so `docker` *and* `docker-compose` both resolve
    and `docker version` even exits 0 — while any real command dies with "The
    command 'docker' could not be found in this WSL 2 distro. We recommend to
    activate the WSL integration in Docker Desktop settings." Probe with an actual
    `docker compose ps`, never with `command -v`. The fix is the per-distro toggle
    in Settings → Resources → WSL Integration (26.04 is OFF).

- **The Windows console here is cp1251.** Any verification script that prints or
  asserts on non-ASCII (emoji labels, ⚠️ captions) dies with `UnicodeEncodeError`
  and masks the real result — set `PYTHONIOENCODING=utf-8` and keep success-path
  prints pure ASCII.
- **Root-owned `__pycache__/*.pyc`** left by a Docker container that ran as root can
  block a plain `rm -rf` of a repo dir on this WSL box, since the WSL `me` user has no
  passwordless sudo — clear them with an interactively-run `sudo rm -rf`.
- **WSL→Windows interop is DISABLED on this box** (probed 2026-07-26).
  `/proc/sys/fs/binfmt_misc/` holds only `register` and `status` — no `WSLInterop`
  entry (systemd is PID 1, which drops the registration). So `/mnt/c` is fully
  readable/writable from WSL but **no Windows `.exe` can be executed**:
  `cmd.exe`/`powershell.exe` give `cannot execute binary file: Exec format error`.
  Anything that must drive Windows (`hosts/desktop/windows/*.ps1`,
  `provision/windows.ps1`, bootstrapping the Windows Claude profile) has to run on
  the Windows side — over SSH, or natively in Git Bash.
- **`C:\Users\methe\machines` is NOT vestigial** — it is the link target for the live
  Windows-native Claude profile: `C:\Users\methe\.claude\{CLAUDE.md, host-memory.md,
  statusline-command.sh}` all point into it. Keep the clone on disk even though it
  need not be registered as an Orca project (it has zero Orca worktrees).
